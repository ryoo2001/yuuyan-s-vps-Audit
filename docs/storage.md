# 存储说明

本文说明中心库的表结构、数据保留期限、归档流程以及新增地区的方法。

## 按地区分库

每个地区对应一个独立的数据库，所有数据库采用同一套表结构，内部版本号为 schema v2。

同一数据库中可以存放多台落地机的数据。每台落地机使用一套带独立前缀的数据表，并拥有独立的上传账号、批次编号（epoch）和序号。例如，落地机 a 和 b 分别对应 `a_samples` 和 `b_samples`，a 的上传账号只能写入 `a_` 前缀的表。

每台落地机的数据表包括：

- 原始数据表（连接、流量、访问记录等）和上传进度表；
- `traffic_monthly` 月累计表，在原始数据新增、修改、删除时由六个触发器自动更新；
- 常用查询所需的索引。

此外，每个数据库还有三张公共表：

| 表 | 用途 |
|---|---|
| `audit_schema` | 表结构版本 |
| `traffic_calendar` | 已迁出数据库部分的月累计 |
| `archive_receipts` | 每个归档文件对应一条记录，包括所属月份、文件名和 SHA-256 |

查询统一通过五个中文视图进行。同一数据库中有多台落地机时，视图会为每条记录附加落地机名称后再合并。由于各落地机的表独立编号，不同表中可能出现相同的 ID，因此不能直接用 ID 跨表关联。

## 数据保留期限

| 时间范围 | 读取方式 |
|---|---|
| 最近 7 天（可调整为 3 至 7 天） | 五个视图默认仅查询此范围 |
| 7 天以前、14 天以内 | 查询时指定时间范围，或直接查询原始表 |
| 14 天以前 | 已迁出至数据库外的月度归档文件，需要时单独读取 |

前两段数据存放在同一张表中，仅按时间区分，不重复存储。

## 归档流程

`central/archive.py` 每 5 分钟检查一次，将超过 14 天的数据迁出数据库，步骤如下：

1. 将待迁出的数据写入压缩文件，并确认已写入磁盘；
2. 重新读取文件，核对内容、行数和校验和；
3. 核对通过后，在同一事务中将该部分数据的月累计写入 `traffic_calendar`，写入 `archive_receipts` 记录，并删除库内对应数据。

任一步骤失败，库内数据均保持不变。

原始表上设有删除前触发器：只有归档程序在核对通过后才能删除数据，其他情况下执行 DELETE 将直接报错（`cold_archive_required_before_delete`）。该机制用于防止未归档的数据被删除，不应为使删除通过而移除该触发器。

归档文件按北京时间月份存放。归档文件及对应的 `archive_receipts` 记录属于正式数据，很可能是唯一副本，并非临时备份，不应作为冗余文件清理。

月累计 = 库内现有数据的累计 + `traffic_calendar` 中已归档部分的累计，计算时无需读取归档文件。

## 新增地区

新地区使用 `central/region.py` 创建数据库，该脚本会建立统一的表结构、触发器和保留规则。创建前需确定数据库名称、落地机的表前缀、上传账号及其权限；创建后需分别验证上传、只读查询和归档功能是否正常。

不应复制现有地区的 SQL 来创建新库，也不应重复执行历史建库脚本。

连接真实 MySQL 的测试为 `central/test_storage_mysql.py`、`central/test_archive_mysql.py`、`central/test_monthbook_mysql.py`，仅可在专用测试库中运行。日常操作的注意事项见 [运维说明](operations.md)。
