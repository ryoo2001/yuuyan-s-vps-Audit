# 运维说明

部署前须先在目标机器上确认实际情况，包括机器身份、服务名称、代码版本、配置、表结构及监听端口。仓库中的配置为原部署环境的示例，不代表机器的当前状态。远程操作优先使用 ops_mcp 提供的专用工具；无对应工具时，方可使用带审计记录的 `ops_ssh_exec`。

## 发布步骤

1. 按实际改动选择对应的 [检查项](validation.md)，先在本地通过。
2. 与机器上现有的代码、配置和服务逐一核对，仅选取本次需要变更的文件。
3. 使用 [发布工具](../deploy/README.md) 生成仅包含上述文件的发布请求，并进行人工审查。
4. 先在单台机器上试运行：将文件放入临时目录，完成编译检查和配置检查，仅重启本次获准变更的审计服务。
5. 确认采集线程正常运行、目标网卡均已被捕获、新连接能够识别客户 IP、中心数据库的确认位置（ACK）持续前进，且代理等其他服务未受影响。全部正常后再处理下一台机器。
6. 记录实际操作时间与范围。验收后清理本次产生的临时文件和回滚备份。

不得重新执行历史的 `deploy/*.json`。`central/init.py`、`deploy/central.py`、`deploy/rename_db.py` 为一次性建库或迁移脚本，不得用于修复现有数据库。`build.py --update` 会覆盖配置和服务文件并重启服务，不属于常规更新命令。

## 故障排查

| 现象 | 优先检查项 |
|---|---|
| 客户 IP 显示未识别 | 入口是否有流量、指纹是否送达终止端、终止端能否唯一匹配 |
| 上传积压 | 上传程序是否运行、是否存在写入错误、确认位置是否前进、批次序号是否正常 |
| 归档停止 | `systemctl list-timers` 中的下次运行时间、归档目录是否已挂载、磁盘空间、校验错误、删除保护是否拦截 |
| 查询缓慢 | 查询时间范围、是否按采集点过滤、索引及月累计；应先测量再调整 |

在没有新流量时，进程存活并不能说明客户识别正常。历史上未识别的记录不得以中转机地址补录；不得通过清空队列、重置 epoch 或删除上传进度来消除告警。

## 归档与备份

归档文件默认位于 `/var/lib/traffic-central/archive`，归档进度记录位于 `/var/lib/traffic-central/state`。归档的前提是目录已挂载、校验通过，且数据库中已写入归档记录。发生故障时应先恢复上述前提，不得关闭删除保护强行删除。备份使用 `central/backup.sh` 及对应的 systemd 定时器，启用前须确认路径、权限、磁盘空间和保留策略。

数据恢复须先在独立测试库中演练，生产库须获得明确授权后方可操作。归档文件可能是唯一副本，不得作为临时文件删除。

## 操作边界

审计故障不构成修改或重启代理、隧道、转发、防火墙、SSH 或数据库容器的授权。停止、删除、恢复生产数据库，修改权限或端口，重建上传进度，均须事先明确范围并取得授权。临时备份仅针对确有回滚需要的文件。
