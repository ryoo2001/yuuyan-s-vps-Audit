# 运维说明

本文介绍发布更新的步骤、故障排查方法、归档与备份，以及禁止的操作。

仓库中的配置为原部署环境的示例，不代表机器的当前状态。操作前应先登录目标机器，确认机器身份、服务名称、代码版本、配置、表结构及监听端口。原部署环境中，远程操作统一通过 ops_mcp 的专用工具进行，无对应工具时才使用带审计记录的 `ops_ssh_exec`。

## 发布步骤

1. 根据改动内容，在本地运行对应的检查（见 [分级校验](validation.md)）。
2. 与机器上现有的代码、配置和服务逐一比对，仅选取本次需要更新的文件。
3. 使用 [发布工具](../deploy/README.md) 生成仅包含上述文件的发布包，并进行人工审查。
4. 先在单台机器上试运行：将文件放入临时目录，完成编译检查和配置检查，仅重启本次需要更新的审计服务。
5. 确认以下各项均正常后，再处理下一台机器：
   - 采集线程正常运行，目标网卡均已被捕获；
   - 发起一条新连接，能够识别出客户端 IP；
   - 中心库的确认位置持续前进；
   - 代理等其他服务未受影响。
6. 记录实际操作的时间与范围，并清理本次产生的临时文件和回滚备份。

`build.py --update` 会覆盖配置和服务文件并重启服务，不适用于日常更新。

## 故障排查

| 现象 | 优先检查项 |
|---|---|
| 客户端 IP 显示未识别 | 入口机是否有流量；指纹是否送达落地机（经中继时检查中继队列是否阻塞）；落地机能否唯一匹配；是否为采集器重启前已建立的长连接 |
| 上传积压 | `publish.py` 是否运行；是否存在写入错误；确认位置和序号是否前进 |
| 归档停止 | 通过 `systemctl list-timers` 查看下次运行时间；归档目录是否已挂载；磁盘空间是否充足；是否存在校验错误；是否被删除触发器拦截 |
| 查询缓慢 | 查询时间范围是否过大；是否按落地机过滤；应先测量耗时所在环节，再考虑调整索引 |

在没有新流量的情况下，进程存活并不能说明识别正常。验证时应有一条真实的新连接完整经过整条链路。

## 归档与备份

归档文件默认位于 `/var/lib/traffic-central/archive`，归档进度记录位于 `/var/lib/traffic-central/state`。归档正常运行的前提是：目录已挂载、校验通过、数据库中已写入归档记录。归档发生故障时，应先恢复上述前提，不应关闭删除触发器强行删除数据。

备份使用 `central/backup.sh` 及对应的 systemd 定时器。启用前需确认路径、权限、磁盘空间和保留份数。

数据恢复应先在独立的测试库中演练；操作生产库须事先获得明确授权。归档文件可能是唯一副本，不应作为临时文件删除。

## 禁止的操作

审计系统出现故障，不构成修改或重启代理、隧道、转发、防火墙、SSH 及数据库容器的理由。此外，以下操作均不应执行：

- 为消除告警而清空队列、重置 epoch，或删除上传进度（`sync_state`、`central_dirty`）；
- 以入口机地址补填历史上未识别的记录；
- 对已投入使用的数据库重复执行 `central/init.py`、`deploy/central.py`、`deploy/rename_db.py`，这些均为一次性建库或迁移脚本；
- 重新执行 `deploy/*.json` 中的历史发布请求，其中可能包含旧版代码；
- 关闭删除触发器强行清理数据。

停止、删除、恢复生产数据库，修改权限或端口，重建上传进度，均须事先明确范围并获得授权。临时备份仅针对确有回滚需要的文件。
